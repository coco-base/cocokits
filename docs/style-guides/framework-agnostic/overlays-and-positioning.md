# Overlays and positioning

What shared layers do, and do not do, for every floating or overlay part: dialog, popover, tooltip, menu, select content, toast. The overlay invariants (portaled, works inside modal dialogs, shadow roots, RTL and theme scope, one positioning module, closed overlays render nothing on the server) are in [docs/architecture.md](../../architecture.md). This page only splits the jobs. Why: [overlays](../../why/overlays.md).

Where the element lives (portal), where it is drawn (positioning) and how it appears and leaves (presence) are separate jobs:

| Job | Owner | Does |
|---|---|---|
| Portal | each `<fw>-core` | The only code that moves DOM nodes |
| Container and host | cdk `portal` | Resolves the container (the document's fullscreen element, else the closest open modal `<dialog>` that contains the trigger, else the trigger's shadow root, else `<body>`), creates the host and keeps its mode attributes and `dir` in sync; never moves nodes other than its own host, which it moves and shows again only on a fullscreen change (known limit: a modal `<dialog>` inside the fullscreen element that holds the trigger makes the moved host inert) |
| Positioning | cdk `positioning` | Computes coordinates for a real or a virtual anchor and writes `position`, coordinates and measured geometry (`--anchor-width`, `--available-width`, `--available-height`, `--transform-origin`) as inline styles, and the place and rotation of an arrow part; takes `sideOffset`, `alignOffset`, `avoidCollisions`, `collisionPadding`, `sticky`, `hideWhenDetached`, `collisionBoundary`, `updatePositionStrategy`, `sideFlip`, `alignFlip`, `prioritizePosition`, `disableUpdateOnLayoutShift` and the arrow options (`getArrow`, `arrowPadding`, `hideShiftedArrow`); never creates, moves or portals elements |
| Stacking and dismiss | cdk `dismissal` | Per-document layer stack that raises one cancelable dismiss intent per cause (`escape`, `outside-press`, `focus-out`) before anything closes; a layer is a barrier when its native dialog is modal or when it is created `modal`; the adapter refuses it with `preventDefault()` or closes. Escape and a native `cancel` go to the topmost layer; an outside press and a focus-out walk the stack from the top down ([dismiss rules](#dismiss-rules)) |
| Focus | cdk `focus` | Tabbable query, focus return, focus guards (with `loop` they wrap Tab inside the content), `makeOutsideInert` (everything outside the given elements gets `inert`, released exactly), focus-visible tracking and the deferred-focus scheduler; the platform traps focus in a modal `dialog` |
| Presence | cdk `presence` | Mount and unmount with exit animations. `waitForAnimations(element)` is the one wait for an element's running, finite CSS animations (transitions, paused, infinite and `element.animate()` animations are not awaited; no timeout), used by the exit and by an adapter that waits for an enter |
| Scroll lock | cdk `scroll-lock` | Ref-counted page scroll lock for modal overlays; it applies only when the page scrolls (the root or a scrolling `<body>`), adds no padding under `scrollbar-gutter: stable`, writes the removed width to `--scrollbar-width` on `<html>` while locked, and a modal holds it until its native dialog has left the document |

## Rules

- Never move or reparent rendered nodes in utils, shared, cdk or machines. The only element a shared layer adds is the per-overlay host, lazily, in the browser.
- Do not assume overlay content is a descendant of the root or the trigger. Find parts through registered element refs and tolerate `null`.
- One host element per overlay, so two overlays from differently themed subtrees carry two theme contexts.
- Decide inside versus outside for dismissal from registered refs (the trigger, the content and nested overlays such as a submenu), never from DOM nesting.
- A modal dialog is the native `<dialog>` opened with `showModal()`: the platform owns inertness and the top layer, and Escape is routed through the layer stack so only the topmost layer closes. The Popover API is used for stacking the portaled element only, never instead of the portal: the per-overlay host is a `popover="manual"` element shown with `showPopover()`, so it sits in the top layer and no ancestor's `overflow` or `transform` clips it. It is one code path in every supported browser, not a fallback.
- The host is appended to the container from the table above, which is inside an open modal `<dialog>` that contains the trigger because a modal makes everything outside its subtree inert, including a top-layer element outside it. A manual popover has no light dismiss and Escape does not close it, so the dismissal module handles Escape on `keydown` (default-prevented, which also stops the dialog's `cancel`).
- Positioning writes `position: fixed`, coordinates and measured geometry only. The options above are optional and have defaults (5 px edge padding, `sticky: 'partial'`, collisions avoided) that every overlay gets at once; `sideOffset` replaces the theme's `--side-offset`. A virtual anchor (`getAnchor` returning a rect with an optional `contextElement`) is positioned and followed on scroll and resize like an element. With `hideWhenDetached` the module only reports through `onAnchorHiddenChange` that the anchor is fully hidden; it writes no `visibility`, `display` or `pointer-events`, and the machine renders the native `hidden` attribute from that fact. With an arrow part (`getArrow`) the module measures it once when it starts, adds its height to the gap, places it on the content edge that faces the anchor and turns it to point at the anchor, and reports through `onArrowHiddenChange` that it cannot point (it writes no `display` or `visibility` on it; the machine renders the native `hidden`). `--transform-origin` is the point where the content meets its anchor (the arrow tip with an arrow). The resolved side and alignment are rendered as `data-side` and `data-align` by the machine from its state, never as `data-placement` and never read from the DOM.
- `aria-controls` on the trigger is rendered only while the content is mounted; `aria-expanded` always reflects the open state. For a default-open overlay the server renders no content, and the content mounts after hydration; server and first client render stay identical.
- A tooltip is described, not named: its text is a description element (`createDescription` in the cdk `portal` module) that lives in the trigger's overlay container, is created in the browser after mount and never on the server, and is not an overlay (no host, no layer). The adapter gives the trigger `aria-describedby` for it and hides the visible content from assistive technology; the element is left out when the text is empty or equals the trigger's `aria-label`. A tooltip closes when an ancestor of its trigger (or the document) scrolls, with reason `scroll`: the content would otherwise detach from its trigger.
- Focus: a modal dialog relies on the native `<dialog>` (the rest of the page is inert, no Tab trap). Non-modal overlays that take focus move it into the content on open and back to the trigger on close. A tooltip never takes focus; a combobox keeps focus on its input.
- An exit completes immediately when nothing animates (no `animationend` or timeout waits), reopening during an exit cancels it, and an exiting overlay stops participating in dismissal and focus.
- Effects that only apply while an overlay is open (positioning, dismissal, focus, scroll lock) stop when it closes. One exception: a modal `<dialog>` is still shown during its exit animation, so its dismiss layer only `exit()`s when it closes (it raises no intent) and stays a barrier, and the scroll lock stays, until the native dialog has left the document; then `destroy()` and unlock. A non-modal layer is destroyed at once.

## Dismiss rules

The cdk `dismissal` module raises a `DismissIntent` (`reason`, `event`, `preventDefault()`) per cause; the adapter's `onDismiss` refuses it by preventing it, otherwise it closes. The cdk never closes anything. A layer declares the causes it listens for (`dismissOn`, default `escape` and `outside-press`; a Popover adds `focus-out`) and may name the layer it opened from (`getParent`, read when the stack is used, so a child registered first still stacks above its parent).

- **Escape** goes to the topmost layer only, in the bubble phase on the document, so an element inside that stops or prevents the keydown keeps every layer open. A keydown during IME composition (`isComposing` or `keyCode` 229) is ignored; a modifier does not block it. A handled Escape is default-prevented, so the native `cancel` does not follow. A `cancel` with no Escape keydown before it (an Android back gesture, assistive technology) is raised as an `escape` intent with the `cancel` event; a `cancel` that follows a keydown an inner element stopped is ignored. A browser that forces the close after a refused `cancel` (its close watcher) fires `close`: the layer raises an `escape` intent with the `close` event that `preventDefault()` cannot refuse, and the adapter closes its state.
- **Outside press and focus-out** walk the stack from the top down, with the stack order and the target taken when the press starts: a layer that contains the target ends the walk (a press on a modal's backdrop does not count as containing); a layer that does not listen is skipped; a modal ends the walk and is collected when it listens. The collected layers get their intents top-down and a refused intent stops the rest, so the layers below stay open.
- **Which presses count.** A press on any scrollbar, a default-prevented `pointerdown`, and on a modal a secondary-button or ctrl+primary press do not dismiss. A touch press is decided at `pointerdown` and dispatched on the `click` that follows, so a scroll, a pan or a long press never dismisses; mouse and pen dispatch in the bubble phase of `pointerdown`, so a target handler that prevents the event keeps the layers open. On iOS the cdk sets `cursor: pointer` on `body` while a listening layer exists, because iOS sends no `click` otherwise.

## Rules for every framework adapter

Each framework file adds only what is specific to it ([angular](../angular/overlays.md), [react](../react/overlays.md), [vue](../vue/overlays.md)).

- The content part renders through the one fw-core portal, never in place. There is no inline mode, no `disablePortal`-style prop and no optional portal part a consumer could leave out or disable.
- Adapter code never imports `@floating-ui/*`. The resolved placement is stored as the adapter's state and the part renders `data-side` / `data-align` from it.
- Containers and anything that needs the DOM are resolved in the browser when the overlay opens, never at import time.
- Dismiss, focus handling and exit animation use the cdk modules. Start them after mount, on the content's element, and stop everything they started in the cleanup.
- Events from the content do not bubble through the trigger's parent; use the content part, emits or outputs, and context.

Overlay tests in every framework: the content is inside the overlay container and not inside the trigger's parent; a trigger inside an open modal `<dialog>` portals inside that dialog; outside press dismisses and inside press does not; focus moves in on open and back on close; a closed overlay renders nothing in server output. Open overlays are queried from the document, not from the component root ([component-tests](../testing/component-tests.md)).

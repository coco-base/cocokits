# Interaction portability

Purpose: when the compiler accepts a story with an event handler: the domain it models, the event and trace tables, the four-step check, how the Angular view is updated and the evidence behind it. The story language is in [story-language.md](./story-language.md).

Angular and Vue listen to the native events and read live values. React has its own event system, reads the values of the render that created the handler, and runs its `onChange` and `onFocus` differently. A story is accepted only when the compiler establishes equivalent author-handler delivery and settled observable behaviour across Angular, React and Vue, with every exception explicit and tested. The compiler is not meant to be the blocker for daily stories: it prints the Angular code so that the three outputs behave alike, and refuses only what no printing can reconcile. "Settled" means after the interaction finishes: the rendered text, attributes and conditional content, the control values, the focused element, and how many times each author handler ran. The frames in between are not compared.

**The domain** is finite: a native `button` and the Button, a text-like input (`type` absent, `text`, `search`, `email`, `url`, `tel`, `password`), a checkbox, a select and an `input` of type `button`; their labels (wrapping and `for`); a `form` with the controls that have a contract (the `form` kind, below); and Tab and Shift+Tab. A component is in the domain when its host element is (`as` included), for the host's native events; its own events, `bind` and a controlled model through it need its delivery contract ([Delivery contracts](#delivery-contracts)). A native `textarea` is not in the story vocabulary, so it is `unknown-component` with or without a handler; a component whose host is a `textarea` renders one, and the host has the events of a text field when the component has a delivery contract (the Textarea has one). The Button is the component the tests run; another component with a native host has the host's events, and its own forwarding needs a contract.

The element x event table. A dash is `event-attribute`: the element refuses the event, with the reason in the message.

| Element | `onClick` | `onInput` | `onChange` | `onFocus`, `onBlur` |
|---|---|---|---|---|
| `button` (`button`, Button, `input type=button`) | `click`: pointer click, Enter and Space each fire it once | – | – | `focus`, `blur` of the element |
| `text-input` | – (the keyboard fires `click` only on a button and a checkbox) | `input`, once per edit (typing, paste, delete) | – (the browser fires `change` on commit, React's `onChange` on every edit: use `onInput`) | `focus`, `blur` of the element |
| `checkbox` | `click`: pointer click, label click and Space each fire it once | `input`, after `click`; React runs it after `onChange` | `change`, after `input`; React runs it with `onClick`, before `onInput` | `focus`, `blur` of the element |
| `select` | – | – | `change`, once per chosen option | `focus`, `blur` of the element |
| `form` | – | – | – | – (a form handles `onSubmit` only, and only a form that holds the controls of a `form()`) |

`onFocus` and `onBlur` are the native `focus` and `blur`. React's bubble to the ancestors and the native ones do not, which the delivery check below turns into a rule. `bind` prints the handler of each framework that writes the state (Angular `(input)`, React `onChange`, Vue `v-model`). On a component with a contract, `bind` is the model's two-way binding and `onValueChange` is the model's change event ([Delivery contracts](#delivery-contracts)).

**Out of the domain.** An author handler on these gets `event-attribute` (a `bind` on a number input gets `invalid-bind`), and the message starts with "out of domain". Static markup of an element in the story vocabulary stays valid; only a handler is refused, and `autofocus` is refused on any element or component. The first column is the `name` of an entry of `OUT_OF_DOMAIN` (`tools/story-compiler/src/interaction/element-events.ts`), the one list of what is refused; a test keeps one row per entry.

| Out of the domain | Why |
|---|---|
| a native input of type `radio` | A radio group (the checkedness of its peers, arrow keys) is covered only through the Radio component, which has a delivery contract (the native input is out of the domain) |
| an input of type `number` | Native number editing differs by browser and locale; a `bind` on it is refused too |
| an input of this type | Any type other than the ones in the domain (`range`, `date`, `file`, `hidden`, ...): only those are modelled |
| an element whose `type` is an expression | The compiler must know the type to know the events |
| a submit or reset control | A `button` of type `submit` or `reset`, or an `input` of type `submit`, `reset` or `image`, with a handler: submitting or resetting is a default action that fires its own events and changes other fields. The control without a handler is in the `form` kind (below) |
| a control with a form owner | Inside a `form`, or with a `form` attribute, without a contract that covers it (a native control in a form; the Button and the components with a contract are covered by the `form` kind for their host's native events and `bind`; a component's change handler in a form is out of the domain): a form adds submit, reset and implicit submission to its controls |
| an `<a>` | A link navigates |
| a `<summary>` | It toggles its `details` itself |
| a textarea host without a contract | Editing (new lines, composition) is covered only through a component with a delivery contract (the Textarea has one). No `textarea` is in the story vocabulary, so only a component whose host is one reaches this row; a native one is `unknown-component` |
| a component with no delivery contract | Its own events (`onValueChange`, `onCheckedChange`), `bind` and a controlled model need a tested contract ([Delivery contracts](#delivery-contracts)); `default<Model>` needs none |
| an element with `autofocus` | The browser focuses the element when it mounts, and React calls `focus()` on every mount while the browser declines once another element has focus: the focus handlers and the focused element could differ |

**The trace table** says what each thing a user does delivers, step by step. A step is one dispatch: in React the handlers of one step run from one render, so they read the same values. `@target` is the element the user acts on, `@above` its ancestors, `@label` its labels, `@from` the element that loses focus. For the rows of a compound component's parts (`composite.*`, `overlay.*`, `select.choose`, `item.activate`) `@target` is the part the user acts on (a tab, a trigger, an option, an item, the content) and `@root` is the root part of its component, which holds the models: the change of a model is delivered there. It is a model of Chromium, which `apps/docs-e2e` runs; it is not a claim about every browser. The sources of each row are in `tools/story-compiler/src/interaction/trace-table.ts`, the single source of this table and of the check. The `summary.pointer` and `summary.key` rows are for the handlers above a summary, which are accepted; a handler on the summary itself stays refused (out of the domain), and a `details` whose summary the browser supplies uses the same rows. `toggle` is the browser opening or closing the `details` after the click; no handler takes it. `submit` is the submission of a form, which the `onSubmit` of a `form()` form takes, and `reset` its reset, which no handler takes; the target of the `form.*` rows is the `form` element. `open` is the change of the `open` model of an overlay (`onOpenChange`), and `event` the event of a part that is not a model change (`onActivate` of a menu item). A closing overlay unmounts its content, so `open` is delivered with or without a handler of the story, and the replacement rule below reads it. The native `select` element's row is `native-select.choose`; `select.choose` is the Select component's.

**Delivery contracts.** A component joins the domain for its own events with a tested contract: one trace row for each user action the stories deliver through it (`bind` and the model's change event, here `text-input.type` for a text field, `choice.pointer`, `choice.key`, `choice.caption` and `radio.arrow` for a box that the user checks, and `select.choose` for a value that the user picks from a list), a `browser-facts` row and a row of the matrix in `apps/docs-e2e/tests/interaction-matrix.spec.ts`, in all three frameworks, for the real component. `default<Model>` needs none, because no handler is involved. A `bind` or a component event handler (`onValueChange`, named after the semantic id of the model's change event in the `ApiDoc`, and the `on<Event>` of a part event) on a component without a contract is `event-attribute` ("out of domain"); a component without a model has no `bind` (`invalid-bind`). The list of contracts is `CONTRACTS` in `tools/story-compiler/src/interaction/contracts.ts`; a test keeps this table the same.

**Composite and overlay rows (the contract mechanism).** The rows of the compound components are generic, so a new composite or overlay adds a `CONTRACTS` entry that lists the rows its user actions follow, a `browser-facts` row and a matrix row for each, and no compiler code. A `part` row applies to the parts it names (`parts` in the trace table) of a component whose contract lists it. The rows: `composite.pointer`, `composite.key` and `composite.arrow` (a tab or an item of a group: the click, Enter and Space, an arrow key, Home or End, then the model change on the root), `overlay.trigger`, `overlay.close`, `overlay.escape` and `overlay.outside` (the click on the trigger or on a Close part, Escape inside the topmost overlay, a press outside every layer, each ending with the change of `open`), `select.choose` (an option chosen: the value, then `open` false for a single Select) and `item.activate` (an item that reports a part event: the event, then `open` false when the item closes its overlay). The entries that have landed are `popover` (`overlay.trigger`, `overlay.close`, `overlay.escape`, `overlay.outside`; measured by `browser-facts/popover-rows.ts` and `popover-contract.spec.ts` on the fixture story `e2e-popover-contract`) `dialog` (the same four rows; `browser-facts/dialog-rows.ts` and `dialog-contract.spec.ts` on the fixture story `e2e-dialog-contract`, where the outside press is a press on the backdrop) and `tabs` (`composite.*`; `browser-facts/tabs-rows.ts`, the matrix in `apps/docs-e2e/tests/tabs-contract.spec.ts`). `select` (`select.choose`, `overlay.trigger`, `overlay.escape`, `overlay.outside`; `browser-facts/select-rows.ts` and `apps/docs-e2e/tests/select-contract.spec.ts` on the fixture story `e2e-select-contract`; the value of a Select is a text, or a list under a literal `multiple`, which `bind` and the change handler take: the `select-value-*` rows measure that a choice writes the value once, then `open` goes false for a single Select, and that a later `set` shows in the trigger) has landed too. A list state read by `each` is read-only content, so a handler inside it never meets a repeat that the update removes (rule R). Each entry lands with the stories of its component, because the facts and the matrix rows are measured on the real component. A Menu would add `item.activate`.

**The `overlay.submit` row (Dialog).** A `method="dialog"` form in the Dialog Content closes the native `dialog` when it is submitted, with no request and no navigation ([HTML, form submission algorithm](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#form-submission-algorithm)): the `submit` event fires first, the dialog closes after it, and `open` is false once. The trace has the target on the form and the models on the root of the Dialog. The `browser-facts` row (`browser-facts/dialog-rows.ts`, `dialog-submit-enter` and `dialog-submit-click`) shows, per framework, that Enter in the field and the submit Button each run the handler once, close the dialog once, report `open` false once and keep the page URL; the matrix row is `apps/docs-e2e/tests/dialog-contract.spec.ts` on the fixture story `e2e-dialog-contract` ("Submit bound" and "Submit handled" give the same settled projection as Close). The evidence is Chromium only.

What the Input contract measures (`browser-facts/input-rows.ts`, `interaction-matrix.spec.ts`; the Textarea contract measures the same on the real Textarea, `browser-facts/textarea-rows.ts` and `textarea-contract.spec.ts`, and adds that a new line reaches the state and the field as one edit): typing, deleting and inserting write the bound state once per edit and the field shows it; a handler gets the text of the field once per edit; the author's `onFocus` and `onBlur` beside a `bind` run once; the text of an IME composition reaches the state when the input method commits it and not when it is cancelled. The order of the component's change event against an author's native handler on the same element differs by framework (Angular runs the component first, Vue and React the author first), so an `onInput` beside `bind` or `onValueChange` on one Input or Textarea is refused. Inside a `form`, their `bind` is covered by the `form` kind (below), and their change handler stays out of the domain.

**The `form` kind** covers a story `<form>` and what sits in it: implicit submission (Enter in a text field), the submit Button, the native reset, and the Button and the components with a contract for their host's native events. There is no `onSubmit` on a plain form, except on a `method="dialog"` form in a Dialog Content, above. The rows are `form.enter`, `form.submit` and `form.reset`; the `browser-facts` rows are `form-rows.ts` (the real Input and Button in a plain form: Enter and a click submit once and the page stays, an empty `required` field blocks the submit with `checkValidity()` false, a reset Button restores the initial values, a Button of type `button` runs its handler and submits nothing) and, for a `form()` in the three frameworks, `form-fields.spec.ts` (a submit of empty fields shows every error and runs no handler, a valid submit and Enter run the handler once, Reset restores the values and hides the errors, a form with no handler marks every field, a read of the validity; and a bound Input and Checkbox that follow a native reset); the matrix rows are `form-contract.spec.ts` on the fixture story `e2e-form-contract` and `form-submit-contract.spec.ts` on `e2e-form-submit` (the submit Button of a `form()`). Every story `<form>` prevents the browser's submit, printed by the compiler, so a story never navigates (a `method="dialog"` form in the Dialog Content is the exception, see the `<form>` row of [story-language.md](./story-language.md)); a plain form prints no `novalidate`, because the three frameworks add none to a form they do not own, so the browser's constraint validation is the same in all of them. The `form()` of the language is in [story-language.md](./story-language.md): Angular prints `form[formRoot]`, which sets `novalidate` and prevents the submit, and the submission action runs only while the form is valid; React and Vue print `noValidate` and a submit that prevents the default, marks every field as submitted and runs the handler when the form is valid, which the facts above show to be the same in the three. A native reset does nothing to a field that `[formField]` binds (the control skips its reset handling when Signal Forms owns it), so the Reset Button of a `form()` form has `type="button"` and `reset(form)`, and a `type="reset"` control inside it is `invalid-handler`. A controlled model prop on a component inside a form is outside the contract: the reset reports of its peers would rewrite it. A `bind` on an Input, a Textarea, a Checkbox or a Switch inside a form is inside it: a native reset restores the component's mount value and the component reports `form-reset` (`text-control-base.ts`, `check-control-base.ts`), so the bound state follows, which `form-fields.spec.ts` shows in the three frameworks and `form-stories.spec.ts` shows on `input/reset-in-a-form`. The Radios of a group each report their own restored check and each report writes the group state, so a Radio `bind` in a form stays refused.

What the Checkbox, Switch and Radio contracts measure (`browser-facts/choice-rows.ts`, `choice-contracts.spec.ts`): their host is a `div` around a native input and its caption, so no native event of the host is authorable (`onClick` on a Checkbox is `event-attribute`); the user toggles the box with the pointer, with Space or with a click on the caption, and the component reports the change of its input, which `bind` and the change handler (`onCheckedChange`) take. A click on the box, on the caption and the Space key each toggle a bound Checkbox or Switch once, a later `set` shows in the box, and a handler gets the new value once per toggle, in the three frameworks. An author handler on a Button around the component runs once for a click on the box and as often for the caption as the component's markup makes the browser deliver it (the Checkbox's caption forwards the click to the box, the Switch's does not), the same in every framework. The controlled checked model ("controlled value, handler sets the read states") is measured on three items and a select-all control: a click on the control sets every item and the control follows, an item unchecked after that leaves the control unchecked, and the Checkbox's mixed state (`indeterminate`, recomputed from the items) is the same in the three frameworks. The RadioGroup is the component that follows a string state, so it holds the contract of the group and a Radio inside it takes no `bind` or handler: a click on another Radio, a click on its caption and an arrow key check it and the group reports its new value once, a click on the checked Radio changes nothing, and a later `set` checks the Radio of that value and unchecks the others (an empty text unchecks all of them). The group reports once for the whole change, so the Events panel of `radio/plan` and `radio-group/controlled` shows one row for each check. Inside a `form`, the `bind` of a Checkbox, Switch or RadioGroup is covered by the `form` kind (above), a native reset restores their mount value and reports `form-reset`, and their change handler stays out of the domain.

**The check** runs once per trace of every element of the story, in four steps. Each finding is `invalid-handler`.

1. Delivery. Every author handler, and the handler `bind` prints, must run as many times in React as in Angular and Vue. This is why a focus handler on an element that holds anything focusable (a control, an `a` with `href`, a `summary`, a `details` (the browser supplies a summary when the story writes none), any `tabindex`, also through a slot or a `when`) is refused: React runs it when the focus enters the descendant and the native event does not. Put the handler on the element that takes focus.
2. Effects. Where the frameworks run two handlers in another order, or React runs them from one render, the pair must satisfy `Wi ∩ Rj = ∅` both ways, with writes that are disjoint or the same constant (`set(x, true)` in both). `W` is what a handler sets or toggles and `R` what its values read, through a derived value too (a `toggle` reads its own state). It is a sufficient rule, not a necessary one: it can refuse a story that would behave, and the answer is to let one handler own the transition.
3. Replacement (rule R). A handler occurrence of a trace that writes a state a mounting condition reads (a `when` condition, a branch or an `otherwise` replacement, through derived values) on the target, the target's ancestors or, in a label trace, the label and its ancestors, may replace a view that contains another handler of the interaction. No other author handler or `bind` may then be delivered on that chain later than the writer, in either framework order. The rule counts per occurrence: a handler delivered twice is two occurrences, a writer at any role counts (the element the focus leaves included), and a handler that has already run in both orders does not (an `onFocus` hint beside an `onChange` dismissal). The finding says the write "may replace a view containing another handler in this interaction": writing the condition does not prove that a view is replaced. The reason is listener lifetime, which no timing can reconcile: React has collected the handlers of a dispatch before the commit, Vue keeps the listeners of a detached element and Angular removes them. A checkbox whose only handler dismisses it is accepted, because that handler is the last one to run in every framework. **The content of an overlay is a mounting condition:** the content part of a component whose root has an `open` model counts as `when(open, …)` around its subtree, where `open` is the state the root binds, or an implicit state of the instance when it binds none, and the change of `open` that the closing rows (`overlay.close`, `overlay.escape`, `overlay.outside`, `select.choose`, `item.activate`) deliver is a write of it, handler or none. A handler inside the content that writes the bound state (a Save `Dialog.Close` with `onClick`) is checked like a self-dismissing control, and so is the `bind` of the root; a handler on an ancestor of the target inside the content that the click reaches after the overlay closed is refused (`<Dialog.Close>` inside a `<Button onClick>` in the content). A handler outside the content, or on a part the trace does not reach, is accepted. An `each` is no mounting condition: its list is a constant and its key is the item, so no update adds, removes or replaces a repeat, and the repeats of one element are one site of the analysis. The rule reads the `when` around or inside an `each`: a handler of a repeat that writes the condition of a `when` on its chain is refused as for a single element, and a writer that no `when` on the chain reads is accepted.
4. Blur by the story's own update (rule B). A blur that the story's update causes is not a step of the interaction. Chromium blurs a focused element at once, inside the mutation, when its own `hidden` is set, when it or an ancestor is removed (a `when`, either branch) and when the `disabled` of an ancestor fieldset is set (a control in the first `legend` of that fieldset is not disabled by it). React's event dispatcher is off during its commit, so React drops the author `onBlur` there; Angular and Vue run it, so the settled page can differ. Every other change blurs at the next rendering update and all three run the handler: its own `disabled`, `inert`, `hidden` of an ancestor, `display`, `visibility` and closing a `details`. No printing fixes the first kind, so for every trace whose target has an author `onBlur`, a handler or `bind` delivered to the target or above it, from the focus step on (the target's own `onFocus` included), is refused when it writes a state that its own `hidden`, a `when` on its chain or an ancestor fieldset's `disabled` reads, and the `onBlur` writes a state the writer does not set to the same literal. The finding says the write "hides or removes the focused element, and React does not run its onBlur then". Precondition: nothing in the story language moves or removes a focused node but a `when` (there is no reordering). An `each` keeps it: its list is a constant and its key is the item, so no update adds, removes or moves a repeat, and a repeat is removed only with the `when` that holds it, which is what the rule reads. A construct that changes a list or moves nodes must revisit this rule.

**When the page updates.** Angular, with no zone, updates the page in a task of its own after a handler; React and Vue update it in a microtask, which Chromium runs after every listener and so before the next step of the same interaction (the focus after a blur, the click after a focus, the `input` after a click, the toggle of a `details` after the click on its summary). The Angular code therefore ends a handler with the update of the story's view, so that the browser continues on the same page in the three frameworks. A handler is eligible when some delivery of it, in some trace and in either framework order, has a later step, or when it writes a state that the `disabled` of its own element reads (through derived values), so that a click that follows at once meets the disabled element. There is no test of what the page reads. React and Vue print nothing extra. Without the update, a handler that hides, removes or disables the next tab stop, closes its `details`, rewrites the `for` of a label or removes its control, writes the `open` of the `details` its summary belongs to, or disables the Button the pointer is on diverges in Angular only; the plain-DOM facts in `tools/story-compiler/browser-facts` pin which of these the browser still honours. How the update is printed, and the names it reserves: [compiler README](../../../tools/story-compiler/README.md) (Angular update of the view).

**Ownership.** All story declarations and story-authored bindings, projected content included, belong to the one generated story component, so its `detectChanges()` updates every view the story can change: its template, its `@if` blocks, the inputs of the components it binds and the host bindings of the directives on its elements. A test over the printed class pins it (`daily-scenarios.test.ts`): one class, no `@Input`, `output`, `viewChild`, `ApplicationRef` or `@defer`, and no `inject` but the `ChangeDetectorRef`. It is not a proof about components the story imports: a component with internal events, mounting, a host or focus of its own needs a tested delivery contract before it joins the domain (above), and the printed class alone does not give it.

**Scope.** The compiler establishes portability for the declared story language, the contracts of the supported components, the pinned Chromium behaviour and settled interactions. "Settled" excludes rapid repeated input before the interaction has finished: the update above also covers a Button that disables itself, but a second click in the same frame of an interaction that is not settled is outside the guarantee in every framework. Expressiveness is a different question and is explicit: the language has no chosen value of a select and no handler payload beyond the value of a component's own event (`onValueChange={(text) => …}`), so "show fields for the chosen option" is written with a state that is toggled.

A finding names both handlers and the state, the trace of the table, and its cause:

| Cause | The message says | Fix |
|---|---|---|
| Delivery difference | `delivery difference: ` and the handler runs never in Angular and Vue but once in React | Move the handler to the element that takes the event |
| Effect conflict | `effect conflict: ` and one handler writes a state that the other reads, or both write it with different values | One handler owns the transition: set the states in it, or give each handler its own state (the rewrites below) |
| Replacement | `effect conflict: ` and the write "may replace a view containing another handler in this interaction" | Let one handler own the dismissal, or keep it mounted and hide a wrapper (`hidden={done}` on the wrapper) |
| Blur by the story's update | `effect conflict: ` and the write "hides or removes the focused element, and React does not run its onBlur then" | Let this handler make the blur's writes, or keep the element in the page: hide a wrapper or disable it |
| Out of the domain | `out of domain: ` and the element (`event-attribute`) | Not available in this version: use an element of the domain |

How to rewrite a refused story.

- Two handlers on one element that share a state: let one handler own the transition and write values, not the state the other handler would read. `set(result, 'x')` on `onClick` and `set(mirror, result)` on `onChange` become one handler that runs `set(result, 'x'); set(mirror, 'x')`. Reading a state after the same handler set it is `read-after-set`, so the merged handler repeats the value instead of reading the state back. Two handlers that set one state to the same constant need no rewrite.
- A checkbox that dismisses itself while another handler of its chain is still to run (a separate counter on `onClick`): give the dismissal to one handler, or keep the checkbox mounted and hide a wrapper.
- A handler that removes or hides an element that has an `onBlur`: make the writes of the `onBlur` in that handler too (`set(touched, true)` in both is accepted), hide a wrapper instead, or disable the element.
- `onInput` beside `bind`: `bind` owns the input, and what the story wants to do on typing is written as what it shows, a `derived` value or a `when` over the bound state, not as an action on each key press. The language has no action that runs on every key press of a bound field.
- A focus handler on an element that holds something focusable moves to the element that takes focus.

Two elements in a chain of ancestors may handle the same bubbling event as long as the pair passes the effects step and rule R (no separate ancestor rule is needed). A Button around a checkbox, both handling `click` with disjoint states, is an analysis fixture of the compiler tests, not an authoring pattern: a checkbox inside a button is not valid HTML. How a self-read such as `set(count, count - 1)` is printed is in the [compiler README](../../../tools/story-compiler/README.md) (Names). An author `onInput` beside `bind` on one input is `invalid-bind`: Vue's `v-model` dispatches one more `input` event when an IME composition ends, so the handler could run once more in Vue.

**Conservative refusals, documented.** Rule R refuses more than it has to, and says so: a dismissal that shares its chain with a later handler, even when the later handler would behave (a label inside a Button whose unmounting meets a checkbox with its own handler runs the same in the three frameworks), and a blur that removes an optional next field that has its own handler (the field is gone before it takes focus in all three, and its `onFocus` runs in none). Each is a row in `portability-mounting.test.ts` and in the framework facts.

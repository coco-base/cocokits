# Overlays in React

Shared rules: [overlays-and-positioning](../framework-agnostic/overlays-and-positioning.md#rules-for-every-framework-adapter). Why: [overlays](../../why/overlays.md).

- The content part renders through the fw-core portal with `createPortal`.
- Inside/outside decisions use registered refs and contexts, never React-tree event bubbling through the portal: the content is not inside the trigger's parent.
- Dismiss, focus handling, positioning and the focus guards start in layout effects of the content part (browser only), keyed on `open`, that read the node from a ref and return a cleanup stopping everything they started. The content stays mounted while `open` turns `false` for the exit animation, so a ref callback would need a new identity on each flip and would detach the author's `ref`.
- The Root keeps the content rendered after `open` turns `false` until the cdk presence reports `unmounted`, and learns whether the content is in the document from a layout effect of the content (the trigger's `aria-controls` follows that fact, so it is absent on the server and in the first client render).
- An overlay opened from inside another overlay's content registers as its child: the content provides its dismiss layer through the one `DismissLayerContext` (`packages/react/src/internal/`) and the nested content reads it as `parent`. Every overlay (Popover, Dialog, Tooltip, Select) uses this context, never one of its own, so overlays of different kinds nest.
- The trigger is stored in Root state by a ref callback, so the content works whatever the order of the parts in the tree. The focus guards are two empty `span tabindex="0"` around the content element, inside the host.
- React context crosses portals unchanged, so theme and direction runtime reads work inside overlay content.
- A modal content (`Dialog.Content`) calls `showModal()` in a layout effect that runs once when the content mounts (not on `open`), starts the dismiss layer (`getNativeDialog`) and the scroll lock in the effect keyed on `open`, and returns focus to the trigger from the cleanup of the mount effect (the dialog is inert until it has left the document); a native `close` the parent refuses is shown again.
- The Select is a compound like the others: `Select.Root` renders the root `div`, the hidden inputs and the validation message, and the author writes `Select.Trigger`, `Select.Value`, `Select.Content` and the items. The trigger keeps DOM focus while the list is open, and the items are mounted only with the list, so each item registers its DOM node (keyboard, typeahead, `aria-activedescendant`) through a context and an opening key waits for them (the highlight starts, and a typed character finds its item, when they have registered). No item registers a label for the Root to render: the trigger text comes from the Root's `items` or `itemToStringLabel`, so it is in the server render. The list lines up with the FormField's input wrapper (`inputWrapper` of the field context) when the trigger is the field's control.
- Tests: [testing.md](./testing.md).
- Direction: `<DirectionProvider dir>` and `useDirection()` from `@cocokits/react-core` (default `'ltr'`); the portal host copies it. `Portal` takes `open` (kept `true` during the exit animation) and `getTrigger`, and gets the mode names from the theme's `modeCollections`.
- **Refuse a dismissal with the Content handlers, the way Radix does.** `Dialog.Content` and `Popover.Content` take `onEscapeKeyDown`, `onPointerDownOutside`, `onInteractOutside`, `onOpenAutoFocus` and `onCloseAutoFocus` (the Popover also `onFocusOutside`); `Tooltip.Content` takes `onEscapeKeyDown` and `onPointerDownOutside`. `event.preventDefault()` refuses; the specific handler runs first, then `onInteractOutside` with the same event, and a refusal keeps the layers below open. The details of `onOpenChange` also have `cancel()` and `isCanceled` (the Base UI way), which refuse an open or a close of an uncontrolled overlay. They are the one generic `CancelableChangeDetails<Reason>`, aliased per component. A close with no key (the `cancel` event) reaches no key handler and is refused with `details.cancel()` or a controlled `open`.
- A Dialog opened by its Trigger returns focus to that Trigger; a Dialog opened another way (without a Trigger, a controlled `open`, the service) returns it to its opener. A Dialog without a Trigger opens; a Popover or Tooltip without a Trigger warns in development.
- Overlay content extends the one `OverlayPositioningProps` interface (`packages/react/src/internal/overlay-positioning.types.ts`: `sideOffset`, `alignOffset`, `avoidCollisions`, `collisionPadding`, `sticky`, `hideWhenDetached`), as `ChoiceControlBaseProps` is shared by the choice controls. The content passes a prop to `startOverlayPosition` only when it is set, so the cdk defaults apply otherwise. `Tooltip.Content` extends it too. `Tooltip.Provider` is optional and renders no element: it sets `delayDuration`, `skipDelayDuration` and `disableHoverableContent` for the tooltips inside it, which share one skip window; a Root prop wins over it. A Popover Anchor with `virtualRef` renders no element and registers the ref as a virtual anchor.
